Nexventory | CS 499 Milestone Three | September 2026

Algorithms and Data Structures Enhancement

Turning quantities and stock targets into a repeatable, tested restocking priority.

Artifact and reason for selection

Nexventory is the Android inventory application I began in CS 360. My experience with Army inventory systems gave me a practical reason to build a clearer way to organize supplies. For this September 2026 enhancement, I built on the software design work from Milestone Two. The original, Milestone Two, Milestone Three, and final source snapshots preserve the progression.

I selected the application because a saved quantity alone does not tell a user which supply needs attention first. Cables, adapters, and switches can have different targets. The enhancement turns inventory records into a repeatable recommendation while keeping the rule understandable to someone planning a restock.

Rules and implementation

Each item has a minimum-stock target. Shortage is max(0, minimum minus quantity), and only a positive shortage makes an item a restocking candidate. Equality means sufficient stock. A zero target disables automatic restocking even when the physical quantity is zero. Physical stock status and a recommendation to reorder are therefore separate decisions.

The priority comparator puts eligible out-of-stock items first, then orders candidates within each group by descending shortage. Case-insensitive product name and saved item ID resolve ties. For example, an Adapter with quantity zero and target four precedes a Patch Cable with quantity three and target ten. The cable has a larger shortage, but the adapter has no available stock. A Label Roll above its target is excluded.

The implementation filters records into an ArrayList and sorts with a Comparator. For n input records and k selected records, this takes O(n + k log k) time and O(k) additional storage. A comparison implementation fills and drains a PriorityQueue. Producing the entire ordered list has the same asymptotic cost with either approach. A queue is useful for repeatedly retrieving the next item; a sorted list is a simpler fit for the current complete display.

The interface adds stock filters, name and quantity sorting, and a Show Restock List action. Searches by SKU, item number, and product name can be combined with the stock filters. Cards show minimum and shortage. Summary counts and optional alert decisions use the same target rule, reducing the risk that different parts of the application disagree.

Evaluation and evidence

The preserved algorithm harness passed 59,321 assertions across the worked example, empty inventories, equality and zero targets, integer boundaries, input validation, filter and sort behavior, comparator properties, and 100 seeded randomized inventories. The list and heap produced equivalent ordered results. The count includes repeated checks inside loops; it is not a count of distinct test methods.

The milestone benchmark generated 100,000 records with 49,509 candidates. After warmup, median processing times were approximately 16.27 milliseconds for the sorted list and 18.39 milliseconds for the drained queue. The final portfolio regression run again passed the harness; its timing record is included separately. These are in-memory desktop measurements, affected by the JVM and host load, and do not measure Android rendering, database latency, or physical-device performance.

The milestone records successful Android Studio unit and connected test tasks. Recorded emulator checks cover saved minimums, priority ordering, tie-breaking, all stock filters, ordinary sorts, SKU search combined with restocking, invalid minimums, cancellation, and logout. The later Room enhancement also reruns the inherited algorithm checks after the model changes.

Reflection and feedback

The main challenge was defining the stock rule before choosing a collection. The previous fixed threshold did not account for different supply needs. The equality and zero-target cases exposed why the display, counts, and alerts needed one consistent rule. Separating the algorithm from Android screens made it easier to test those decisions without running the application for every case.

My Module Six journal records a 40/40 result for the algorithms milestone, with sound coding and logic and no requested corrections. I retained the graded algorithm and refined the explanation of complexity, repeatable ordering, and measurement limits. Further work could consider equipment criticality, lead time, or cost. A larger inventory would also justify improving the screen's per-record view construction.

Course outcomes and boundaries

Outcome three has direct support in the comparator rules, data-structure comparison, complexity analysis, and test evidence. Outcome four is supported by isolated algorithm logic and repeatable verification. Outcome two is supported by the worked example, code review, and documentation. Validation and nonnegative stock constraints contribute to outcome five. Outcome one has review documentation and instructor feedback, while the broader collaboration discussion belongs in the self-assessment.

This enhancement does not implement supplier-aware procurement, category or location search, or a guarantee of phone performance. The final portfolio keeps those limits visible so the evidence supports the claims actually made.
