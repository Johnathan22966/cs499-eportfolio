Nexventory | CS 499 Milestone Two | September 2026

Software Design and Engineering Enhancement

Improving the inventory workflow while preserving existing accounts and records.

Artifact and reason for selection

Nexventory is the Android inventory application I created in CS 360 and enhanced during CS 499 in September 2026. The reviewed baseline already contained account screens, SQLite inventory storage, stock summaries, and optional SMS code. I selected it because improving an existing application required me to understand its current behavior and preserve useful work while addressing usability, structure, and security problems. Its focus on technical supplies also connects my Computer Science coursework with my networking background.

This category is represented by the preserved Milestone Two source. The final database version carries these improvements forward, but the separate snapshot makes the scope of this enhancement visible. My earliest plan described some account and storage functions as unfinished; the reviewed source and code review are the more accurate baseline.

Changes and demonstrated skills

I added search tabs for SKU, item number, and product name. Bound query values protect the search boundary, and SQL wildcard characters are escaped when a user intends a literal name or SKU search. Inventory cards expose the item's identity, quantity, and stock status. Editing starts with the saved values, field labels clarify the expected input, and an empty search returns an explanatory message.

Deletion requires confirmation, and Cancel leaves the record unchanged. Quantity validation happens before integer conversion so an oversized value produces an error instead of a crash. Required fields and database rules reject incomplete or negative inventory values. The InventoryRepository gives screens a consistent boundary for inventory access. Fifteen labeled networking sample records can be added and removed through controlled actions.

The original application stored account passwords in plain text. The enhancement stores a unique random salt and a PBKDF2-derived hash for new accounts and migrates existing passwords without deleting accounts or inventory. Logout and session checks improve navigation through protected screens. SMS preferences are saved and checked alongside Android permission before a send request. The message reports a request rather than claiming confirmed delivery. These changes demonstrate defensive input handling, separation of responsibilities, state management, and attention to the user's understanding of an action.

Learning and challenges

The most useful lesson was that a feature needs to handle unexpected input and cancellation as carefully as the usual path. A quantity that looks numeric can still exceed the application's integer range. A search term can contain characters with special SQL meaning. A delete dialog can be closed without permission to remove the item. Handling these cases explicitly made the application more predictable.

Password migration showed why a software improvement must account for information already stored. Recreating the database would have made the new schema simpler but lost the user's records. Preserving accounts while changing how passwords are verified required coordinated changes to storage and login behavior. Similarly, changing a notification label from delivered to requested made the interface more accurate without claiming a delivery confirmation the application did not possess.

Verification and feedback

The submitted narrative records a successful Android Studio build and manual checks of all three search modes, item editing, logout, sample removal, and SMS preferences. Oversized quantities displayed an error while preserving the saved value, and delete cancellation retained the item. Four baseline inventory records remained after the sample records were removed. These are recorded milestone observations rather than a claim that every workflow was rerun during the final portfolio revision.

My Module Six journal records that this milestone was submitted and graded; a separate detailed instructor comment for this category is not present in the supplied materials. I have therefore kept the verified enhancement scope and clarified its narrative rather than attributing a specific requested correction to the instructor. The later database stage includes further tests of the inherited storage and account behavior.

Course outcomes and boundaries

Outcome four is supported by the repository boundary, completed inventory workflows, and practical verification. Outcome five is supported by password migration, bound queries, validation, and session checks. Outcome two is supported by the code review, this narrative, and readable technical notes. Preserving the baseline and explaining review findings supports the review strategies in outcome one, while an individual enhancement alone does not establish diverse team collaboration. Outcome three is developed more directly in the algorithms category.

The original plan's broader category and location searches, barcode lookup, and serialized-equipment model are not presented as completed features. Inventory remains shared between accounts. Session checks and password hashing improve this educational application but are not a complete production authorization or data-protection design.
