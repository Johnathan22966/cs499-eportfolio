Professional self-assessment

Connecting networking experience with software engineering, algorithms, databases, and security.

Professional direction

My Computer Science education has helped me connect my experience in Army satellite communications and networking with a broader understanding of how technical systems work. I currently work as a network engineer, and my goal is to continue toward advanced network engineering and cybersecurity positions. Completing the program has expanded how I approach that goal. I now look beyond connectivity to the applications, algorithms, databases, and security decisions that make a system dependable.

My professional values center on accurate information, clear communication, and changes that can be verified. Experience with Army inventory systems gave me a practical reason to improve how supplies are organized. The capstone gave me a structured way to turn that concern into software and explain the decisions behind it. Developing this portfolio also required me to distinguish a proposed feature from an implemented feature and a successful test from a claim that still needs evidence. That discipline is directly useful when planning and reviewing changes to a working network.

Collaboration and stakeholder communication

While working as an instructor, I frequently encountered technical problems as new terminals were introduced. Gaps in knowledge meant that other instructors and I needed to work with the terminal engineering teams to troubleshoot. In one case, reaching a terminal's graphical user interface required an older SSL configuration, so browser settings had to be changed before the interface could be accessed. The newest terminal update supports access with both the older and newer configurations. This experience showed me why instructors and engineers need to share their different perspectives: instructors need a procedure they can teach and use, while engineers need a clear account of the compatibility problem. It also taught me to distinguish a temporary access workaround from an updated system capability and to revisit instructions when the equipment changes.

A collaborative technical environment needs a shared understanding of the problem before people choose a solution. My CS 499 code review establishes that starting point by walking through the existing application, identifying weaknesses, and explaining planned improvements. Preserving the original source and each enhancement stage lets a reviewer check what changed instead of relying only on my description. Written decision records explain the reason for a choice, the alternative considered, the evidence used, and the remaining limits.

I adapt the explanation to the person using it. A developer needs the query, migration rule, and repeatable test. An inventory user needs to know which item needs restocking and whether an import saved any records. A reviewer deciding whether to accept a change needs both the benefit and the risk. The restocking example, plain-language narratives, readable source pages, and verification records provide those different entry points. Clear labels, explicit error messages, and documented assumptions also reduce the amount of specialized knowledge someone needs to participate in a review.

Instructor review was the formal feedback channel for this capstone. My Module Six journal records full marks for the algorithms and database milestones and no requested corrections. I retained their core behavior and used the final revision to clarify the presentation and evidence. The capstone was an individual development project, while my instructor experience provides a concrete example of working across technical roles to solve problems. Together, these experiences shape how I would support a review environment: make the problem understandable, invite the relevant expertise, and give people enough evidence to decide what to do next.

Algorithms and the evaluation of alternatives

The program strengthened my ability to define a problem precisely before choosing a data structure. In the capstone, a restocking recommendation depends on an item's own target, its available quantity, and consistent tie-breaking rules. A zero target disables automatic restocking, while zero physical stock still describes an out-of-stock item. Making those distinctions explicit prevented different screens from applying conflicting rules.

I evaluated a sorted ArrayList against a PriorityQueue that is filled and drained to produce the same complete ordered result. Both have O(n + k log k) time for n input items and k candidates, with O(k) additional storage. The sorted list fits the current display because the user sees the full ordered list. The preserved benchmark covers up to 100,000 generated records, and the algorithm checks include 59,321 assertions with randomized inventories and boundary cases. Those results support a specific design choice; they do not establish performance on every device. This is the kind of explicit tradeoff I want to bring to network automation and troubleshooting tools.

Software engineering and databases

I have learned to treat maintainability, data preservation, and testing as part of a feature. Separating screens, inventory rules, repository access, and database operations makes a change easier to reason about. Database upgrades need to preserve saved identities and account access as well as create the new schema. Importing a file needs a defined response to invalid rows and duplicates. These concerns connect software engineering decisions with the reliability of the information a user depends on.

My work outside this portfolio's selected artifact includes the CS 465 Travlr project. That project connects an Express API, an Angular administration interface, and MongoDB. Its Module Seven authentication work distinguishes public reads from authenticated changes and uses API responses, route protection, and verification records to explain that behavior. Working with that architecture broadened my perspective beyond a local Android application. It reinforced the need to understand how a user action crosses the interface, application logic, and storage boundaries.

Security as an engineering responsibility

A security mindset means looking for ways a system can fail even when the normal workflow appears correct. Across the program, I have become more attentive to input boundaries, access decisions, and the information exposed by stored data. My networking background makes those questions practical: a dependable system requires more than a working interface.

In Nexventory, the improvements include salted password hashing, bound query values, session checks, database constraints, and bounded CSV input. Transactions prevent an unexpected import failure from leaving an incomplete batch. The implementation still has limits. Inventory is shared across accounts, the local database is not encrypted by the application, and the saved login state is not a complete authorization system. The inherited password-hashing configuration also deserves a separate production hardening review. Identifying these limits is part of responsible engineering, and I would address them before using the application for sensitive organizational inventory.

How the portfolio fits together

This portfolio presents one artifact, Nexventory, developed through all three required enhancement categories. The software design work improves everyday inventory tasks and account handling. The algorithms work adds an explainable restocking decision. The database work moves persistence to Room and introduces migration and transactional CSV import. Together, they show how usability, logic, and stored information depend on one another.

The code review provides the original analysis. The preserved source snapshots show the progression, the narratives explain what I learned, and the verification records support the technical claims. My next steps are to complete my degree, continue developing my networking and cybersecurity skills, and apply the same habits of explicit requirements, careful review, and repeatable verification in my professional work.
