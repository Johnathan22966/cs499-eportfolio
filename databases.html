Nexventory | CS 499 Milestone Four | October 2026

Database Enhancement

Explicit upgrades and transactional imports for more reliable saved information.

Artifact and reason for selection

Nexventory is the Android inventory application I created in CS 360. This October 2026 enhancement builds on the software design and restocking work completed for CS 499. I selected it because reliable storage is necessary for both everyday inventory tasks and useful restock recommendations. Category and location also make the application more useful for organizing networking supplies.

The package preserves the original project and the Milestone Three starting version alongside the final Room implementation. This makes the database changes distinguishable from the features already present before this milestone.

Database design and migration

Room now manages the SQLite database through InventoryRecord and UserRecord entities and InventoryDao and UserDao interfaces. Queries use bound values, and Room checks declared queries during compilation. DatabaseHelper preserves a compatibility boundary for the repository while delegating storage operations to Room. Category and location are optional descriptive fields on each inventory record; this enhancement does not claim a normalized category or location catalog.

Database version four has explicit migration paths from versions one, two, and three. Upgrades preserve inventory and account IDs, names, SKUs, quantities, existing stock targets, password hashes, and sequence high-water marks. Earlier versions without a minimum receive the inherited default of five. Category and location start blank. Version-one plain-text passwords are converted using the inherited salted hasher. There is no destructive migration fallback.

The migration handles saved information as part of the design, rather than treating a new empty database as a successful upgrade. Invalid negative legacy stock causes the upgrade to fail rather than silently discard or rewrite the records. This preserves evidence of a problem but means the data must be corrected before that installation can upgrade.

CSV import and data integrity

The Android file picker accepts UTF-8 CSV input. The required header is name,sku,quantity,minimum_stock, in that order. The extended header adds category,location, and each row then contains six fields, with optional descriptions allowed to be empty. The parser supports quoted commas, escaped quotes, and embedded line breaks.

Import limits include 1 MiB of input bytes, a decoded character limit, 1,000 data rows, and 512 characters per field. Stock values must be nonnegative 32-bit integers. Required fields, malformed records, and duplicate SKUs are rejected. SKU identity remains case-sensitive, consistent with the inherited schema. A duplicate in the file or existing inventory rejects the whole batch rather than silently updating an item.

After validation, duplicate checks and inserts run inside one database transaction. If any write fails, every row in the batch rolls back. Database triggers also guard integer stock values and nonempty names and SKUs on writes that bypass the screen. Unique indexes protect usernames and SKUs. Database and password work runs on a serial background executor, with checks to avoid delivering obsolete results to closed or superseded screens.

Reflection and verification

This work taught me that a database upgrade has to preserve relationships between identity, account access, and user expectations. Preserving an item's current ID is not enough if a previously deleted higher ID can unexpectedly be reused. CSV import introduced another challenge: splitting at every comma would corrupt a quoted product name. Separating parsing, validation, and transaction handling made those concerns easier to examine and test.

The recorded database verification includes 427 standalone CSV assertions and 59,321 inherited algorithm assertions. Thirteen JUnit tests passed, including three Room tests in a simulated Android environment. The application and instrumentation APKs built. A separate connected emulator run passed six tests, covering actual migrations, saved records, account behavior, and transaction rollback. The final portfolio revision reruns the standalone checks and preserves the historical Gradle and emulator records without presenting them as new runs.

Recorded hands-on checks include saved category and location edits, exactly two valid imported rows, duplicate rejection, rejection of a negative quantity, full restart persistence, search, stock filters, and import cancellation. Physical-device behavior and SMS delivery were not verified. The records also identify manual checks that were not repeated in that database session, rather than marking the entire manual checklist complete.

Feedback and course outcomes

My Module Six journal records a 40/40 database milestone result and no requested corrections. I retained the tested implementation and updated the final narrative to explain the transaction policy, evidence, and remaining limits. The final portfolio now presents the database category alongside the other two enhancements rather than leaving it as planned work.

Outcome four is supported by Room, structured access, and practical bulk entry. Outcome five is supported by validation, bound queries, constraints, migration discipline, and transactional writes. Outcome three is supported by the explicit tradeoff between rejecting an entire invalid import and allowing partial results. Outcome two is supported by this narrative, migration and import pseudocode, and verification instructions. Review material contributes to outcome one, while direct evidence of diverse team collaboration remains more limited than the technical evidence.

Inventory remains shared between accounts. CSV import adds new items and does not update existing ones. Category and location are stored and displayed but are not additional search modes. Serialized equipment tracking, database encryption, per-account authorization, and CSV export remain future work. These boundaries keep the final claims consistent with the implementation.
